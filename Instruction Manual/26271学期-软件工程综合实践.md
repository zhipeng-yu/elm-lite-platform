## 一、课程实践项目基本信息

- **时间**：26271小学期，共3周，第1~3周，2026-08-31 ~ 2026-09-20
- **项目名称**：轻量级外卖服务平台（仿饿了么）
- **TDD**：全程TDD测试优先开发
- **小组规模**：3–4人/组
- **核心技术栈（参考）**：后端 SpringBoot + MyBatis/MyBatis-Plus，前端 Vue3 + Vue Router + Element UI，数据库 MySQL/PostgreSQL，测试工具 JUnit5、MockMvc、Postman/ApiFox
- **前后端接口**：本实训强烈建议遵循 RESTful，但不是教条式死守全部理论，区分「必须遵守」「建议遵守」「可以妥协」。
- **核心考察目标**：贯彻TDD开发流程、掌握前后端分离架构、训练**架构应对需求变更的扩展性**
- **交叉验收测试**：多小组并行开发；**组与组之间交叉验收**，替代教师单一验收；客观可打分
- **全过程控制**：要求分组后立即创建GIT仓库，从仓库更新中考察用户贡献度，不允许临交作业前集中上传代码等。

## 二、对项目应用 AI 辅助编程的态度
> AI 是辅助工具，不能替代学生理解、设计、TDD 流程、架构思考；鼓励合理使用，但设置边界与考核约束，适配教学目标：考察架构应对需求变更、TDD 开发、REST 接口、小组协作、交叉验收。

### （1）鼓励使用 AI 的场景（允许、提倡）
AI 用于**降低重复机械劳动，把学生精力聚焦软件工程核心能力**。

1. **脚手架、样板代码生成**
- SpringBoot 项目初始化代码、DTO、Entity 实体类、基础 Mapper；Vue 页面模板、axios 请求封装。
- MockMvc、Vitest 测试样板代码、统一返回结果封装、全局异常处理器。
2. **语法纠错、Bug 定位**
- 编译报错、依赖问题、Vue 语法问题、数据库 SQL 优化建议。
- 解读报错堆栈，给出修改方向。
3. **方案启发**
- REST 接口设计思路参考、TDD 测试用例思路启发；需求变更下架构改进建议。
- 学生必须对 AI 输出做甄别、修改，不能直接原样复制。
4. **文档辅助**
生成接口文档初稿、实训报告初稿、交叉验收报告模板。学生自行校对修正。

### （2）严格限制 / 禁止直接照搬的场景（考核红线）
>核心教学目标：TDD 红‑绿‑重构流程、架构设计应对多变需求、小组设计决策，这部分不能交给 AI。
1. ❌ 不能直接复制 AI 生成完整业务逻辑就提交：Controller、Service 核心业务逻辑必须小组理解、调整。
2. ❌ 禁止 AI 直接生成全套 TDD 测试用例直接使用：
>TDD 本质思维是：**先分析需求，定义接口行为，写出测试，再实现代码**。
如果直接让 AI 一次性生成测试 + 业务代码，就破坏 TDD “先测试后编码” 的训练目的。
正确用法：AI 给测试思路，学生自己编写 / 修改测试用例，再写业务代码。
3. ❌ 不能由 AI 完成架构决策：接口划分、分层方案、如何处理需求变更，必须小组讨论确定，AI 仅作参考建议。
4. ❌ 不允许 AI 代替小组完成交叉验收工作：Bug 分析、接口评审、测试结果判断由学生小组完成。

## （3）教学考核配套规则
1. **AI 使用要求与溯源**
	小组需要简单记录 AI 辅助使用点：哪些样板代码、哪些 bug 修复借助 AI；不需要逐行记录，但要说明哪些部分参考 AI 产出。
2. **代码不等于得分，重点考察过程证据**
	打分不完全看系统能不能跑通。重点看：
- Git 提交历史：测试用例是否早于业务代码提交（TDD 证据）
- 架构设计文档、需求变更分析文档（小组思考产物）
- 交叉验收表现、对代码的解释答辩：学生要能够讲清楚接口、测试、业务逻辑。
>即使 AI 生成可运行代码，如果学生无法解释代码逻辑，依旧扣分。
3. **防止 AI 带来的负面问题**
- AI 生成的 REST 接口经常不规范，学生需要对照 REST 检查清单做修正；
- AI 生成测试用例往往只覆盖正常场景，缺少异常、权限、边界场景，小组需要补充完善；
- AI 容易产出过度复杂代码，小组要做精简，保持项目适配 3 周实训规模。

## 三、团队分工
- **后端架构&TDD负责人**：负责项目架构搭建、分层规范（Controller/Service/Dao/Entity）、全局异常处理、统一返回结果、所有接口单元测试编写、适配需求变更的架构优化
- **后端业务&数据库负责人**：负责数据库设计、SQL编写、业务功能开发、数据校验、迭代需求功能落地、接口联调
- **前端&验收文档负责人**：负责页面开发、前后端联调、交互逻辑实现、项目文档、测试报告、验收材料整理
- **测试&迭代适配专员**：专职完善TDD测试用例、回归测试、需求变更影响分析、代码重构、BUG

## 四、分阶段需求设计

### 阶段1：基础固定需求（第1周，架构打底，TDD落地）

目标：完成核心架构搭建、基础功能开发、全套基础测试用例，保证架构规范、代码解耦，为后续需求变更迭代铺垫基础
#### 核心功能模块

1. **用户模块**：用户注册、登录、个人信息查询/修改（账号密码校验、状态校验）
2. **商家模块**：商家注册，商家开店/关店/临时闭店等
3. **店铺模块**：店铺列表、店铺详情、店铺状态展示（营业/休息）
4. **商品模块**：商品管理、商品分类、商品列表、商品详情、价格展示、库存展示
5. **基础购物模块**：加入购物车、购物车增删改查
6. **基础订单模块**：创建订单、订单状态查询、订单列表

#### 阶段1强制TDD要求

所有接口、核心业务方法**先写单元测试用例（断言成功/失败场景）**，再开发业务代码，测试通过率100%方可提交代码，留存测试日志和测试类文件。

### 阶段2：需求变更迭代（第2周，核心考核点）

模拟企业需求临时变更，新增、修改原有业务规则，**不允许大面积重构代码**，考察架构分层、解耦、扩展性设计能力，是本实训核心考核项。

#### 阶段2强制要求

需求变更后，必须**新增对应测试用例+原有功能回归测试**，保证迭代后旧功能不失效，体现TDD迭代开发流程。

### 阶段3：功能完善、重构优化、交叉验收（第3周）

1. 针对前两周需求迭代产生的代码冗余、耦合问题，进行**代码重构**，优化架构，提升系统扩展性
2. 完善前后端交互细节、页面美化、异常提示、数据校验
3. 完成全套测试、编写项目文档、整理迭代记录、准备标准化验收
4. 可选高阶拓展

## 五、TDD测试优先开发规范（硬性要求）

1. **流程强制顺序**：梳理业务接口需求 → 编写测试用例（正常场景、异常场景、边界场景） → 运行测试（全部失败） → 开发业务代码 → 再次运行测试（全部通过） → 提交代码
2. **测试覆盖要求**：核心业务接口覆盖率100%，关键业务方法覆盖率≥90%
3. **留存材料**：所有测试类、测试报告、测试日志，需求迭代后的回归测试记录，缺一不可
4. **禁止行为**：禁止先开发后补测试、禁止测试用例无断言、禁止跳过测试直接提交功能

## 六、项目架构设计（适配需求变更）

### 1、后端分层架构（严格规范，降低迭代耦合）

采用标准SpringBoot四层架构，为需求变更提供扩展性：
- Entity：实体类，对应数据库表，支持字段拓展
- Mapper/Dao：数据访问层，仅负责数据库操作
- Service：业务逻辑层，核心业务、规则迭代全部在此，与控制层解耦
- Controller：请求接收、参数校验、响应返回，不写复杂业务逻辑

### 2、通用统一封装（应对高频需求变更）

- 统一全局异常处理器：新增业务异常无需重复编写捕获逻辑
- 统一返回结果类：code、msg、data结构化返回，前端适配无需频繁改代码
- 工具类封装：时间处理、参数校验、状态判断通用工具，迭代复用

### 3、前端架构规范

- 路由分层、组件化开发：公共组件（导航栏、空数据展示、弹窗）复用
- 接口统一封装：axios统一请求拦截、响应拦截，后端接口变更前端无需大面积修改

## 七、前后端接口规范

### 为什么本项目要做 RESTful
1. **接口契约清晰，便于小组协作**
	后端按照资源定义接口，URI 以资源为中心，GET 查、POST 创建、PUT/PATCH 更新、DELETE 删除。前后端不用反复沟通自定义动词 URL（如`/createOrder`、`/updateGoods`）。
	多人开发、3‑4 人小组拆分任务，接口语义一目了然；交叉验收的时候，别的小组一看 URL 就知道接口意图，降低验收理解成本。
2. **天然适配需求变更与架构扩展**
- URL 版本`/api/v1/`，后续破坏性迭代升级`/api/v2`，旧接口保留；
- 资源扩展：新增优惠券、退款，新增资源路径即可，不修改原有接口；
	正好匹配题目考察点：**架构设计应对需求多变**。
3. **非常适配 TDD 测试编写**
	REST 依靠 HTTP 方法、状态码、统一 JSON 返回体。MockMvc 集成测试可以直接断言 HTTP 状态码、资源行为。
	测试用例描述 “对某个资源做什么动作，应当返回什么状态”，语义自然。如果是自定义 RPC 风格接口（`/orderCreate`），TDD 测试只能看业务返回 code，丢失 HTTP 语义。
4. **交叉验收有客观评判标准**
	交叉验收小组可以直接检查：URI 命名、HTTP 方法使用、状态码、分页、鉴权头，有明确检查清单，打分客观，不是主观评价。

## 哪些是**必须遵守**
1. 资源名词 URI，拒绝动词型路径：
	✅ `/api/v1/orders`
	❌ `/api/v1/createOrder`、`/api/v1/updateOrder`
>例外：登录`/users/login`这类动作型接口行业普遍妥协。
2. HTTP 方法语义尽量正确：
- GET 只做查询，不能修改数据；
- POST 用于新建资源；
- PUT 全量更新，PATCH 局部更新；
- DELETE 用于删除资源（业务逻辑删除）。
3. 使用标准 HTTP 状态码，统一响应体格式。
4. 版本隔离：`/api/v1`，应对后续需求变更。
5. 分页、过滤、排序使用 Query 参数。

## 哪些地方**允许妥协，不要教条**（不用死抠）
1. **业务动作接口**：取消订单、支付订单
	理论 REST：`DELETE /api/v1/orders/{id}`代表删除订单；但业务语义是**取消订单（状态变更，不是删除资源）**。
	行业常规妥协写法：`POST /api/v1/orders/{orderId}/cancel`
>不要强行用 PUT 去修改订单状态字段，业务动作语义优先。这是允许的，交叉验收时不扣分。
2. 不强制 HATEOAS（超媒体返回）
	HATEOAS 是 REST 成熟度最高级别，实际项目几乎很少实现，**学生实训完全不需要实现**。
3. PUT 不一定严格实现全量字段更新，开发成本高，实训可以用 PATCH 为主做局部更新。

## 四、不遵循 RESTful 会带来什么问题
1. 接口命名混乱，每个人按自己习惯写 URL，小组沟通成本暴涨；
2. TDD 测试只能依赖自定义业务 code，丢失 HTTP 协议语义；
3. 需求变更的时候，接口随意修改，没有版本管理，老功能容易被破坏；
4. **交叉验收很难客观评判**，缺少统一检查标尺。

## 八、客观量化验收标准

### 1、TDD开发规范

- 严格遵循测试优先流程，有完整测试用例留存
- 核心接口测试覆盖率100%，边界场景全覆盖
- 需求迭代后完成回归测试，无旧功能失效

### 2、基础功能实现

用户、店铺、商品、购物车、基础订单功能全部可正常使用，无BUG。

### 3、需求变更适配能力（核心考核项）

- 通用迭代需求全部落地
- 随机差异化变更需求落地）
- 架构无严重耦合，需求迭代无需大面积重构代码，代码整洁规范

### 4、项目架构与代码质量

分层清晰、命名规范、代码注释完整、封装合理、无冗余代码、全局统一配置完善。

### 5、文档与交付完整性

包含项目说明文档、数据库设计文档、TDD测试报告、需求迭代变更记录、团队分工与开发日志。

### 额外加分项

完成高阶拓展功能、代码重构优化效果优秀、测试覆盖率超95%、页面交互完善美观。
